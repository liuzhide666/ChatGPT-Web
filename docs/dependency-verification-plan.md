# Gradle dependency verification — locked but not authenticated

Baseline: GitHub `dependency-baseline-candidate` run `39028691360`, generated against a clean Android API 37 / JDK17 / Gradle 9.3.1 / AGP9.1.1 Probe Debug build on 2026-10-17.

- Artifact `gradle/verification-metadata.xml` records **367 dependency components and 645 SHA-256 digests**. It includes GeckoView `153.0.20260810162159`, Android Gradle Plugin and its build-time transitive modules. No dynamic/SNAPSHOT coordinate, duplicate component, missing artifact SHA-256 or wildcard trust exemption was found by the structural validator.
- The digests have `origin="Generated by Gradle"`. This is trust-on-first-use for downloaded repository bytes, **not** independently audited publisher provenance. No claim of vulnerability freedom or verified PGP signing is made (`verify-signatures=false`). Review additions against vendor release checksums/PGP as available before future releases.
- The standard `android-build` workflow now checks metadata structure and uses Gradle's default strict dependency-verification mode (no `--write-verification-metadata` in routine CI); unexpected dependency bytes or new artifacts should fail instead of auto-accepting.
- To intentionally upgrade deps, use the **manual-only** read-only candidate workflow. Inspect the generated diff, explain each changed coordinate/digest, then submit a separate PR. Do not automatically overwrite the checked-in metadata, disable verification, or use generic trusted-artifact exemptions.
- This still does not establish build bit-for-bit reproducibility, private release-signing, native library compatibility or HarmonyOS 7 device readiness.
